Module engine 

Source
Expand description

Engines as plugins: one EngineAdapter per coding-agent CLI, each a pure function from a LaunchRequest to a LaunchPlan. Core applies the plan’s workspace actions and starts the process, so an adapter is unit-testable without a filesystem or tmux.

id → adapter. Ids are unique; registration order does not matter.

How to start the engine: program args…, extra environment, and workspace preparation.

What core asks an engine to turn into a command line. Borrowed: launch is pure.

Enums§

WorkspaceAction
Filesystem preparation core performs before starting the process. Relative paths resolve against the session’s cwd; a path that escapes cwd is refused.

Traits§

EngineAdapter
One coding-agent engine. Two required methods; no I/O in launch. Send + Sync so a core can be shared across threads.

apply_workspace
Applies actions in order against cwd. Every target path is checked before anything is written, so a bad action late in the list leaves the workspace untouched.
normalize 🔒

resolve_in
path against cwd, both normalized lexically (. and .. folded), refused if the result leaves cwd or cwd is not absolute. Lexical on purpose: it never touches the filesystem, so the check happens before any write. It cannot see symlinks; adapters are trusted code and core canonicalizes cwd before launching, which is as far as a lexical check can go.
