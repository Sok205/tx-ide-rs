Modules§

config
CoreConfig: everything the library needs, handed in by the caller. The library never reads the process environment.
core
TxCore: the public operations. One struct, built once by open, owning its collaborators.
engine
Engines as plugins: one EngineAdapter per coding-agent CLI, each a pure function from a LaunchRequest to a LaunchPlan. Core applies the plan’s workspace actions and starts the process, so an adapter is unit-testable without a filesystem or tmux.
error
The one error type every public operation returns.
events
Events: what happened to one session. Every mutation produces Events that go to the operation log (<state_dir>/log.jsonl, one compact JSON line {"ts","actor","type","id","name","msg"} per event, appended with a single write on an O_APPEND descriptor so concurrent writers never tear a line) and then to every in-process EventSink.
plugin
The plugin host. One trait, Plugin; a Registry with four slots (engines, event sinks, verbs, resources); a PluginConfig the front end fills from its own config format. Core never parses arguments or reads the environment: a Verb receives argv already split. A resource is a named static blob the core stores and lists but never reads.
profile
Profiles: a list of role names resolved against search dirs into one system-prompt text plus the skill directories the roles grant. <dir>/<NAME>.md from the last dir that has it is the base; every dir’s <NAME>.local.md extends it, in dir order. A role file may open with a frontmatter block whose skills: [a, b] line (at any indent, so tx: nesting works) grants skills; each resolves to <skill_dir>/<name>/ from the last skill dir that has it.
session
The session record: what core stores on disk for every managed session.
